## 性能：大文件打开提速 + 编辑重渲染 39.6ms → 4.46ms（功能不增不减）

用户两条相邻诉求：「加快大文件打开速度」+「保持功能不变，提高整体操作响应速度」。
根因同一：**Python 侧控件对象个数**（flet 的 `build_controls_on_demand` 只让 Flutter
客户端懒建 widget，Python 侧 `controls` 仍是全量构造；3 千行构造控件树 ≈2.4s，95% 花在
flet 内部 `_configure_dataclass`）。

1. **解析走快速构造器**：`models/document.py` 新增 `new_segment` / `new_line` /
   `new_document`（`object.__new__` + `__setattr__` 直填，跳过 dataclass 构造与
   observable 逐字段通知；`segments` / `lines` 仍包装 `ObservableList`，字段类型对齐）。
2. **行视图窗口化**：只构造 `[0, hi)`，`hi` 随滚动按块外扩（`_WINDOW_INITIAL=160` /
   `_WINDOW_MARGIN=40` / `_WINDOW_CHUNK=120` / `_WINDOW_ACTIVATE=200`）；窗口上界单调
   不减；表格块边界对齐 `_snap_window`；对比标签不窗口化。
3. **未构建区用 `ListView.padding`，不用占位控件**（关键修正）：占位控件是**列表项**，
   而 `build_controls_on_demand` 下 `maxScrollExtent` 由「已布局项平均高 × 项数」外推、
   **只认真正布局过的项** → 占位落在布局窗口外就永远不计入。实测 1555 行文档 `max`
   只有 4793（真值 ≈50000），文档后 90% 滚不到。改 `padding`（常量、零列表项）后
   `max` 精确（60482），单次重渲染 **39.58ms → 4.46ms**，列表项 1555 → 160。

真机验证（真实 App + 1750 行文档）：首屏 items=138、max 不退化、滚到底窗口覆盖
(0,1750)、padding 与窗口同步收缩至 0、窗口单调外扩不回缩。全量 1407 → 本次 1416 通过。

## 视觉：标签行与大纲头部等高，顶栏连成一条水平带

### 问题
「标签行高度与大纲顶部高度保持一致」——改前真机实测（`PrintWindow` 整窗抓屏 + 逐列
行程编码）：标签行内容 44px、大纲头部内容 32px，两条底边线相差 **12px**，编辑区与大
纲列交界处有可见台阶，顶栏被切成两段。

### 根因
标签行高度由**最高子项**决定，而关闭 /「+」按钮原用 `ft.IconButton`——Material 最小
点击区给它 **40px 固有高**（`visual_density=COMPACT` 也只降到 32），把标签行顶到
`40 + 上下 padding 2×2 = 44`；压内边距完全无效。与 `views/code_block.py` 头部
「顶部行过高」同款故障。

### 改法
- 新增跨模块常量 `styles.TOPBAR_H = 32`（= 大纲头部的内容固有高），两处都显式定高到它
- `views/tab_bar.py`：`_ICON_BTN = 22`，图标按钮改固定尺寸 `Container(ink=True)`
  （水波/tooltip 不变，去掉 Material 40px 下限）；标签容器 `height=TOPBAR_H` 使激活态
  底色直达底边线；「+」按钮同样定高 + `alignment=CENTER`
- `views/outline_panel.py`：头部改为「定高内容带（`height=TOPBAR_H`）+ **外挂** 1px
  底边线」。**坑**：`Container(height=H, border=bottom 1px)` 的总高**就是 H**（边线被算进
  H 内，内容带只剩 H-1），而标签栏的边线本就在内容带之外 → 直接套会差 1px（实测 33 vs 32）

### 真机验证
内容带均 56 物理 px（dpr=1.75 → 32 逻辑 px），**底边线同为第 108 物理行（差值 0）**；
标签标题 / 大纲标题 /「+」墨迹中心同落 `y=16`（内容带中线）；标签底色直达底边线无缝隙；
关闭按钮与「+」未被裁切。

### 测试与固化

  `IconButton`/`Dropdown`、底边线共线（内容高 + 上下 padding + 边线宽三者相同）、

## 工程教训
- 本环境下 `git stash` 之后 `.git/refs/heads` 与 `pack/*.pack` 曾丢失（疑为按轮次打
  检查点的工作区机制重写 `refs/`，reflog 无 stash 记录）。恢复路径：reflog 取 `main`
  权威 SHA 重写 `.git/refs/heads/main` → 从回收站按 pack 尾部校验和比对找回 `.pack`
  （git 的 pack 文件名就是其内容校验和；`.idx` 的最后 20 字节是 idx 自身校验和，
  pack 校验和在其**前** 20 字节）→ `git verify-pack` 通过后放回 → 删除陈旧的
  `multi-pack-index`（纯派生缓存，与现存 pack 不一致会报 `failed to load pack entry`）。
